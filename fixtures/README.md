email here is fictional (`@example.com`). Generated by `python tools/make_fixtures.py`; do not
edit the JSON by hand (a test checks the generator reproduces it byte for byte).

| file | real PayPal call it stands in for |

## What each case means

- `clean_match`: Payment clearly belongs to one open invoice. NW-1001..1010 carry the invoice number (rule 1); NW-1011..1012 match on exact amount plus payer email (rule 2).
- `partial_payment`: Half of a 1200.00 invoice paid; 600.00 still due.
- `overpayment`: 495.00 received for a 450.00 invoice (rush tip in the note). Expected agent proposal: `refund_overpayment`.
- `duplicate_payment`: Double checkout: two 800.00 captures 98 seconds apart for one invoice. The second is the refund candidate. Expected agent proposal: `refund_capture`.
- `payment_without_invoice`: Money received with no invoice behind it (a deposit and a small licence sale). Expected agent proposal: `create_draft_invoice`.
- `overdue_unpaid`: Sent invoices past their due date (as of 2026-11-07) with no payment. Expected agent proposal: `send_reminder`.
- `fee_only_difference`: Payer sent 500.00 minus PayPal's fee (482.06); difference equals the fee.
- `payer_email_differs`: Invoice went to ap@lumen-bakery; the owner paid from a personal address. Only the memo ('Lumen Bakery - October website retainer') links them, so the AI resolves it. Deterministic rules leave it unmatched; the AI layer resolves it.
- `different_currency`: NW-1022 is a clean EUR match. NW-1023 is a USD invoice paid in EUR (920.00 EUR for 1000.00 USD), so it is flagged rather than matched.
- `refunded_transaction`: Paid, then fully refunded (T1107 row points back to the original; original status V).
- `pending_transaction`: eCheck not cleared yet (status P); not counted as paid.
- `open_not_due`: Sent invoices that are not due yet; no action.
- `draft_invoice`: Never sent; ignored by matching and collections.
- `non_sales_transaction`: Withdrawal to the bank (T0400); not a customer payment, ignored.
